# 多截图分析用户习惯与意图实现方案

## 一、核心理念

### 为什么多截图分析是智能助手的核心？

1. **单一截图的局限性**
   - 缺乏上下文连贯性
   - 无法识别用户真实意图
   - 无法区分偶然行为与习惯行为

2. **多截图分析的优势**
   - 捕捉行为时序演变
   - 识别重复模式和习惯
   - 基于历史行为预测未来意图
   - 理解用户工作流程和思维方式

3. **模拟人类认知过程**
   - 持续观察而非单一判断
   - 建立记忆和学习能力
   - 形成对用户的整体认知模型

## 二、系统架构设计

### 整体架构

```
客户端层 → 数据采集层 → 数据处理层 → 分析引擎层 → 知识构建层 → 交互决策层
```

### 核心组件

1. **截图采集器**：定时或触发式捕获屏幕
2. **数据预处理器**：压缩、过滤敏感信息
3. **图像分析引擎**：识别屏幕内容和活动
4. **时序分析引擎**：分析行为序列和模式
5. **用户模型构建器**：构建用户习惯和偏好模型
6. **交互决策引擎**：决定何时以何种方式交互

## 四、数据模型设计

### 1. 核心数据实体

- **截图分析结果**：单张截图的分析信息
- **行为序列**：连续多张截图形成的行为序列
- **用户习惯模型**：长期积累的用户习惯特征
- **知识图谱**：用户、应用、活动间的关系网络

### 2. 数据关系

- 多个截图分析结果 → 形成行为序列
- 多个行为序列 → 构建习惯模型
- 习惯模型 + 上下文 → 预测用户意图

## 五、分析流程设计

### 1. 多层次分析框架

- **单图分析层**：识别应用、活动和内容
- **短时序列分析层**（5-10张截图）：识别当前任务和工作流
- **长时序列分析层**（数小时到数天）：识别习惯和模式
- **用户画像层**：构建用户工作和学习习惯模型

### 2. 模式识别算法

- **时间模式识别**：识别每日/每周规律
- **行为序列模式**：识别常见操作序列
- **上下文切换分析**：检测任务切换和注意力分散

### 3. 意图预测模型

- **基于历史的预测**：分析历史数据中的因果关系
- **基于时间的预测**：考虑时间因素（时间、日期、工作日/周末）
- **基于上下文的预测**：结合当前任务和环境因素

## 十、成本估算

### 1. 基本参数

- 每小时截图数量：3张
- 每天观察时间：12小时
- 每张截图大小：约200KB (压缩后的JPEG)
- 每次分析附带文字：约500字

### 2. 单次分析消耗

- 输入tokens：1451 (包含图片和文字)
- 输出tokens：482

### 3. 阿里云通义千问视觉大模型价格（qwen-vl-plus）

- 输入成本：0.0015元/1K Token（Batch使用半价）
- 输出成本：0.0045元/1K Token（Batch使用半价）
- 最大输入：129,024 Token数（图像最大16384）

### 4. 每日消耗计算

- 每日截图总数 = 3张/小时 × 12小时 = 36张/天
- 每日输入tokens = 1451 × 36 = 52,236 tokens/天
- 每日输出tokens = 482 × 36 = 17,352 tokens/天

### 5. 每月成本

- 输入成本 = 52,236 × 30 × 0.0015/1000 = 约2.35元/月
- 输出成本 = 17,352 × 30 × 0.0045/1000 = 约2.34元/月
- 总成本 = 约4.69元/月/用户

如果使用Batch模式（半价）：
- 总成本约为2.35元/月/用户

### 6. 优化建议

1. **智能截图触发**
   - 只在屏幕内容发生显著变化时才进行截图
   - 可以减少30-50%的截图数量

2. **分层分析**
   - 使用轻量级本地模型进行初步筛选
   - 只将有价值的截图发送到云端进行深度分析
   - 可能减少40-60%的API调用

3. **批量处理**
   - 将多张截图合并为一次API调用
   - 减少请求次数和固定开销

4. **缓存常见场景**
   - 对于重复出现的场景，使用本地缓存的分析结果
   - 可能减少20-30%的API调用

## 十一、本地图片质量筛选（可用/垃圾图片判定）

本地进行图片有效性筛选，避免将无价值截图上传云端，降低成本并提升整体信噪比。实现代码位于：
- `pkg/screenshot/quality/analyzer.go`
- `pkg/screenshot/quality/metrics.go`

### 1. 输出与数据结构

- __Result__（`quality.Result`）：
  - `Score`：0-100 综合评分
  - `IsJunk`：是否垃圾图片（不建议上传）
  - `Reasons`：判定依据列表（便于日志与调参）
  - `Hash`：aHash 64-bit，用于与上一帧对比
  - `Sharpness`：清晰度（拉普拉斯方差）
  - `Contrast`：对比度（亮度标准差）
  - `Uniformity`：均匀度（基于熵的反向值，0-1，越大越单色）
  - `Mean`：亮度均值（0-255）
  - `Flatness`：平坦度（接近均值像素占比，0-1）
  - `EdgeDensity`：边缘密度（强边缘像素占比）
  - `ChangeHamming`：与上一帧 aHash 的海明距离
  - `BlockVarRatio`：小方差网格块占比（大面积纯色）
  - `Colorfulness`：颜色丰富度（Hasler-Suesstrunk 简化）

### 2. 指标定义与计算方式（`metrics.go`）

- __清晰度 Sharpness__：3x3 拉普拉斯卷积响应方差。
- __对比度 Contrast__：灰度亮度标准差。
- __均匀度 Uniformity__：基于灰度直方图熵（max=8）的反向归一化，范围 0-1。
- __均值 Mean__：灰度均值（0-255），用于近黑/近白检测。
- __平坦度 Flatness__：像素值落在均值±delta 范围内的比例（delta=5），近灰/单色趋高。
- __边缘密度 EdgeDensity__：基于拉普拉斯响应阈值（25）的强边缘像素占比。
- __BlockVarRatio__：将图像划分为 `grid×grid`（默认16×16）小块，统计亮度方差小于阈值（20）的块占比；高占比代表大面积纯色/灰屏。
- __颜色丰富度 Colorfulness__：Hasler-Suesstrunk 指标简化版，越大表示色彩越丰富；纯灰/单色趋近小值。
- __aHash/海明距离__：8×8 平均哈希得到指纹，帧间用海明距离衡量差异。

### 3. 默认阈值与权重（`analyzer.go`）

- __阈值__：
  - `MinSharpness = 25.0`
  - `MinContrast = 18.0`
  - `MaxUniform = 0.92`
  - `MinChange = 6`
  - `MaxFlatness = 0.88`
  - `MinEdgeDensity = 0.005`
  - `NearBlackMean = 5.0`
  - `NearWhiteMean = 250.0`
  - `LowContrastStrong = 10.0`
  - `UniformMax = 0.95`
  - `BlockVarGrid = 16`
  - `BlockVarThr = 20.0`
  - `BlockVarMaxRatio = 0.85`
  - `MinContrastStrong = 16.0`
  - `MinChangeStrong = 4`
- __权重__（总分 100）：
  - `WeightSharpness = 35`
  - `WeightContrast = 25`
  - `WeightChange = 25`
  - `WeightContent = 15`（由均匀度反向映射）

### 4. 评分与归一化

- 对 `Sharpness`、`Contrast`：`normalize(value, min, 3*min) ∈ [0,1]`
- `ChangeScore = clamp(hamming/32, 0, 1)`（hdist 大于 32 按 32 处理）
- `ContentScore = 1 - clamp(uniformity, 0, 1)`
- 综合得分：`Score = 35*Sharp + 25*Contrast + 25*Change + 15*Content`，裁剪到 `[0,100]`。

### 5. 垃圾图片判定规则（任一命中或综合过低）

- __硬阈值严重不达标__：`sharpness < 0.6*MinSharpness` 或 `contrast < 0.6*MinContrast` 或 `uniformity > 0.98`。
- __近黑/近白__：`mean <= NearBlackMean` 或 `mean >= NearWhiteMean`。
- __近灰/单色__：`flatness >= MaxFlatness` 且 `contrast <= 0.8*MinContrast`。
- __边缘极少__：`edgeDensity <= MinEdgeDensity` 且 `contrast <= 0.9*MinContrast`。
- __近单色（熵反向）__：`uniformity >= UniformMax`。
- __大片纯色__：`BlockVarRatio >= BlockVarMaxRatio`。
- __低色彩度__：`colorfulness <= 7.0` 且（`edgeDensity <= 0.006` 或 `contrast <= 18.0`）。
- __重复帧__：已初始化且 `hamming < MinChange/2` 或 `hamming < MinChangeStrong`。
- __综合分过低__：`Score < 55`。
- 以上命中原因均写入 `Reasons`，便于调参回溯。

### 6. 判定流程（本地实时运行）

1. __输入__：截图字节或 `image.Image`。
2. __解码与灰度化__：统一为灰度，降低计算量。
3. __计算指标__：`Sharpness/Contrast/Uniformity/Mean/Flatness/EdgeDensity/BlockVarRatio/Colorfulness/aHash`。
4. __与上一帧对比__：计算海明距离 `hdist` 与 `ChangeScore`。
5. __计算综合得分__：按权重聚合并裁剪。
6. __应用规则__：基于上述多指标强规则与分数阈值，输出 `Result{Score, IsJunk, Reasons, ...}`。
7. __更新状态__：记录当前 `Hash` 作为下一帧对比基准。

### 7. 集成方式与调用点

- 在 `pkg/screenshot/service.go` 的回调中，先调用 `quality.Analyzer.AnalyzeBytes(result.ImageData)`。
- 若 `IsJunk == true`，跳过云端分析；否则进入阿里云视觉模型。
- 可在服务启动时创建 `Analyzer` 单例，按会话/屏幕维度维护，也可在长时间静默或锁屏后调用 `ResetState()`。

### 8. 配置、监控与调参

- __配置化__：阈值与权重支持配置文件/环境变量注入（例如 `MIN_SHARPNESS`、`MIN_CONTRAST`、`MAX_UNIFORM`、`MIN_CHANGE`）。
- __指标埋点__：上报 `Score/Sharpness/Contrast/Uniformity/hdist` 分布与 `IsJunk` 比例，结合真实效果持续调参。
- __日志__：打印 `Reasons` 仅在调试或采样场景，避免日志噪声与泄露风险。

### 9. 性能与边界处理

- 极小图片或解码失败：直接判定为垃圾并打点。
- 高均匀度壁纸/暗场：可能被误判，需结合 `ChangeScore` 与窗口检测策略共同决策。
- 静止但重要的画面（如长文档阅读）：可放宽 `MinChange` 或将场景白名单化（编码器层策略）。

### 10. 预期收益

- 本地丢弃无效截图 40-60%，云端调用与带宽显著下降。
- 有效提升下游识别的平均质量与上下文价值密度。
- 成本进一步降低，与“十、成本估算”联动评估节省比例。
